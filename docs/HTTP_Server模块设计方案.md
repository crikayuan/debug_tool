## 一、需求理解

用户的原始描述：

> 我这边启动 http 的 server 客户端，可自定义端口，然后我的 client 可以将数据传过来我能看到。

拆解为三条硬需求：

| # | 需求 | 含义 |
|---|---|---|
| 1 | **本机起 HTTP 服务** | 用本机当服务端，不是去连别人的服务 |
| 2 | **端口可自定义** | 现场设备/脚本可能约定固定端口 |
| 3 | **能实时看到客户端发来的数据** | 这是核心价值 —— 请求内容要看得清、看得全 |

**隐含的第 4 条**（很重要，容易漏）：客户端发完请求后会等响应。如果服务端不返回合理响应，对方程序大概率**报错、重试或判定失败**，现场调试就变成"数据收到了但对方说失败"。所以必须支持**配置返回什么响应**。

**典型使用场景（码头现场）**：现场 PLC / 网关 / 摄像头 / 第三方系统，配置了一个回调地址（如 `http://192.168.4.61:8080/api/report`），要验证它到底发了什么内容、格式对不对、什么时候发的。

## 二、参考工具调研（GitHub）

这类工具在开源界的标准叫法是 **"本地 webhook inspector / HTTP request inspector"**。调研结论：

| 项目 | 语言/栈 | 值得借鉴 |
|---|---|---|
| **[hookcatch](https://github.com/nguyenminhduc9988/hookcatch)** | **Python 纯标准库**（`http.server`），零依赖 | 与本项目技术栈一致：仅绑 `127.0.0.1`、内存保留最近 N 条、线程安全、`/_/requests` 提供 JSON |
| **[tarampampam/webhook-tester](https://github.com/tarampampam/webhook-tester)** | Go + 内置 React UI | **可自定义响应码 / 响应头 / 响应体 / 响应延迟**；WebSocket 实时推送；多存储驱动 |
| **[5amfung/webhook](https://github.com/5amfung/webhook)** | TanStack + React + shadcn/ui | UI 参考：**滑动详情面板**、JSON 自动美化、一键复制、实时 SSE 推送 |
| **[hookpilot](https://github.com/colapsis/hookpilot)** | Python + **FastAPI** | 同样思路用 FastAPI 实现（我们已有 FastAPI，可参考其路由组织） |
| Hookradar / hooktrap / hookrelay 等 | Node/Go | 通用形态一致：**抓取 → 列表 → 详情 → 重放/转发** |

**关键区分**（决定了设计方向）：

| 工具类型 | 代表 | 用途 |
|---|---|---|
| **主动测试型** | `httpbin`、Postman Echo | 有**固定端点**，用来测"我发出去的东西对不对" |
| **被动接收型** | `webhook.site`、`hookcatch`、RequestBin | 接收**任意路径任意方法**，用来测"别人发来的是什么" |

**本需求属于第二类**，所以设计参考 webhook.site / hookcatch 那一派，**不是** httpbin。

## 三、功能清单

### P0 — 一期必做

| # | 功能 | 说明 |
|---|---|---|
| F-01 | 启动 / 停止 HTTP 服务 | 独立线程运行，不阻塞主程序 |
| F-02 | 端口自定义 | 默认 8080；**启动前检测占用**，避开本程序自用的 20001+ 段 |
| F-03 | 绑定地址可选 | `0.0.0.0`（所有网卡，局域网可访问，**默认**）/ `127.0.0.1`（仅本机） |
| F-04 | **接收任意方法、任意路径** | GET/POST/PUT/DELETE/PATCH/HEAD/OPTIONS 全收 |
| F-05 | 实时请求列表 | 时间 / 方法 / 路径 / 来源 IP / 大小 / Content-Type，逐条实时出现 |
| F-06 | **请求详情** | Body（JSON 自动美化 / 表单 / **二进制按 HEX 显示**）、Headers、Query、完整原始报文 |
| F-07 | **响应配置** | 状态码 / Content-Type / 响应体 / 响应延迟；默认「**回显收到的内容**」 |
| F-08 | **访问地址展示** | 启动后直接显示「本机地址 + 局域网地址」，一键复制（告诉客户端往哪发） |
| F-09 | 筛选与搜索 | 全部 / JSON / 表单 / 二进制 分类切换 + 按路径或 IP 关键字筛选 |
| F-10 | 计数与清空 | 请求总数、接收数据量、运行时长；计数清零、记录清空 |
| F-11 | 导出日志 | 导出到本地文件，文件名含时分秒（沿用现有日志命名规范） |

### P1 — 建议做

| # | 功能 | 说明 |
|---|---|---|
| F-12 | 请求详情「复制内容」 | 一键复制 body（调试时常要贴到别处） |
| F-13 | 按路径分组统计 | 一眼看出哪个接口被调用最多 |
| F-14 | 收藏 / 标记 | 重要请求打标，避免被刷掉 |
| F-15 | 记录上限保护 | 内存保留最近 N 条（默认 2000），超出自动淘汰 |

### P2 — 二期可选（本期不做）

| # | 功能 | 说明 |
|---|---|---|
| F-16 | HTTPS / 自签证书 | 现场设备多用 HTTP；需要时再加 |
| F-17 | 请求重放 / 转发 | 把收到的请求转发到另一个地址 |
| F-18 | 按路径配置不同响应 | 多套 Mock 规则 |
| F-19 | 访问鉴权 | Basic / Token 校验 |
| F-20 | 公网隧道 | 接 ngrok / cloudflared，让外网能访问 |

## 四、UI 设计

### 4.1 定位与布局

作为**第五个顶级模式「HTTP Server」**，与现有四个模式并列：

```
[网络调试] [串口调试] [MQTT调试] [网络扫描] [HTTP Server]
```

该模式下**隐藏右栏** —— 右栏那 8 个模块（快捷指令 / 批量发送 / 自动应答 / Modbus 等）都是"发数据"用的，而本模式是"收数据"，用不上。与「网络扫描」模式的处理一致。

**只用两栏**：左栏设置 + 中栏请求区。

```
┌ 调试助手  [网络调试][串口调试][MQTT调试][网络扫描][HTTP Server]   [●运行中·8080] ┐
├──────────┬────────────────────────────────────────────────────────────────────┤
│ 服务设置  │ ● 本机 http://127.0.0.1:8080 [复制]  局域网 http://192.168.4.61:8080 [复制] │
│  端口 8080│ 任意方法 / 任意路径                                                  │
│  绑定地址 ├────────────────────────────────────────────────────────────────────┤
│ [启动][停止]│ 请求记录 (12)  [全部|JSON|表单|二进制]  [筛选      ]  [导出][清空]    │
│          │ ┌────────────────────────────────────────────────────────────────┐ │
│ 响应配置  │ │时间    │方法│路径              │来源 IP      │大小│Content-Type   │ │
│  状态码   │ │10:23:01│POST│/api/device/report│192.168.1.50 │1.2K│application/json│ │
│  类型/延迟│ │10:23:05│GET │/health?deep=1    │192.168.1.51 │ 0B │—              │ │
│  ☑回显   │ └────────────────────────────────────────────────────────────────┘ │
│          │ ┌ 请求详情 ──────────────────────────────────────────────────────┐ │
│ 统计     │ │ POST /api/device/report  来自 192.168.1.50  10:23:01  1.2KB     │ │
│  总数/流量│ │ [Body] [Headers] [Query] [原始]                     [复制内容] │ │
│          │ │ {                                                              │ │
│          │ │   "device": "plc-01",                                          │ │
│          │ │   "temp": 23.5                                                 │ │
│          │ │ }                                                              │ │
└──────────┴─└────────────────────────────────────────────────────────────────┘─┘
```

### 4.2 三个设计要点

**① 连接信息条放在最显眼处（F-08）**
启动服务后，中栏顶部立刻显示「本机地址 + 局域网地址」，各带一个复制按钮。这是用户最需要的信息——否则还得自己去查本机 IP 再告诉客户端。有多个网卡时，列出所有可用地址。

**② 详情区固定在下方，不弹窗**
参考 `5amfung/webhook` 的滑动详情面板思路，但改成**常驻下方区域**：列表和详情同屏可见，点一条看一条，不用来回关弹窗。四个 Tab（Body / Headers / Query / 原始）覆盖全部调试需求。

**③ 二进制内容按 HEX 显示（F-06）**
现场设备可能发二进制帧（非文本）。这类内容如果按文本渲染会是一堆乱码，所以检测到 `application/octet-stream` 或非法 UTF-8 时自动按 **HEX 显示** —— 与本项目「默认 HEX 发送」的习惯一致。

### 4.3 视觉规范

完全沿用已定稿的按钮体系与配色：主色 `#2f6fed`、方法标签按语义着色（GET 蓝 / POST 绿 / PUT 橙 / DELETE 红 / PATCH 紫）、运行状态绿点、面板标题主色竖条、圆角 9~10px。**不新造样式**。

## 五、技术方案

### 5.1 核心决策：用 Python 标准库 `http.server`，不用 FastAPI/uvicorn

| 方案 | 评价 |
|---|---|
| **① 标准库 `ThreadingHTTPServer`** ✅ 采用 | 零依赖；与主服务（20001）**完全隔离**（独立线程、独立端口、独立 socket）；任意方法/路径通吃；打包零风险。`hookcatch` 就是这么做的 |
| ② 再起一个 uvicorn 实例 | 需要动态注册 catch-all 路由，且两个 uvicorn 在同一进程里管理更复杂 |
| ③ 把 catch-all 挂进主 FastAPI app | **不行** —— 会与主程序的 `/api/*` 路由冲突，且用户自定义端口无法实现 |

**关键点**：本模块需要一个"什么都收"的服务端，这与主程序"提供固定 API"的定位完全不同，**必须独立进程内线程**，不能混进主 app。

### 5.2 后端结构（新增 / 改动）

| 文件 | 改动 | 职责 |
|---|---|---|
| `services/http_server_service.py` | **新增** | `HttpServerManager`：服务生停、`ThreadingHTTPServer` 子类、请求记录队列、响应策略 |
| `routes/http_server.py` | **新增** | REST 接口（start / stop / status / requests / clear / export） |
| `routes/websocket.py` | 改 | 追加 `/ws/http/{session_id}` 实时推送 |
| `main.py` | 改 | 注册路由（**必须在 SPA catch-all 之前**） |
| `models.py` | 改 | `HttpServerConfig` / `HttpResponseConfig` |
| `config.py` | 改 | 默认端口、记录上限、单请求体上限 |

**接口设计**

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/api/http-server/start` | 启动，body 为 `{port, bind, response:{code, content_type, body, delay, echo}}`；端口占用返回明确 4xx |
| POST | `/api/http-server/stop` | 停止 |
| GET | `/api/http-server/status` | 运行状态 + 实际监听地址列表（含所有网卡 IP） |
| GET | `/api/http-server/requests` | 全量请求记录（供刷新/重连恢复） |
| POST | `/api/http-server/clear` | 清空记录 |
| POST | `/api/http-server/export` | 导出日志（复用现有目录选择） |
| WS | `/ws/http/{session_id}` | 新请求实时推送（沿用现有 50ms 轮询 + 1s heartbeat 模式） |

**WS 帧格式**

```json
{"type":"request","item":{"id":"...","time":"10:23:01","method":"POST","path":"/api/report",
  "ip":"192.168.1.50","port":51234,"size":1234,"content_type":"application/json",
  "headers":{...},"query":[...],"body":"{...}","body_hex":"7B 22 ...","binary":false}}
{"type":"status","running":true,"port":8080,"addresses":["http://127.0.0.1:8080","http://192.168.4.61:8080"]}
```

### 5.3 请求处理流程

```
客户端 ──HTTP请求──▶ ThreadingHTTPServer(独立线程)
                          │
                          ├─ 解析 method/path/headers/query/body(raw bytes)
                          ├─ 记录入 deque（线程安全，上限 N 条）
                          │      └─▶ WS 50ms 轮询 ──▶ 前端实时渲染
                          └─ 生成响应（回显 or 自定义）──▶ 返回客户端
```

### 5.4 依赖

**零新增依赖**，全部标准库：`http.server` / `socketserver` / `threading` / `collections.deque` / `json` / `urllib.parse` / `csv`。

## 六、风险与对策

| # | 风险 | 影响 | 对策 |
|---|---|---|---|
| 1 | **Windows 防火墙拦截入站** | **高** —— 用户会以为"程序坏了"（客户端连不上，界面无反应） | ①UI 明确提示需放行；②启动失败/无请求时给出排查提示；③文档写明首次启动要允许防火墙 |
| 2 | 端口被占用 | 中 | 启动前检测，占用时给出明确错误（区分"本程序占用"与"其他程序占用"） |
| 3 | 慢客户端 / 超大 body 拖垮服务 | 中 | 限制单请求体上限（默认 10MB，可配置）；设置 socket 超时 |
| 4 | 客户端发 HTTPS | 中 | 一期不支持 HTTPS，文档明确说明；对方要求 HTTPS 时属二期 |
| 5 | 高频请求刷爆界面 | 中 | 记录上限 N 条 + 前端渲染上限；沿用「暂停显示」能力 |
| 6 | 二进制 body 显示乱码 | 中 | 非法 UTF-8 或 octet-stream 自动按 HEX 显示 |
| 7 | 与本程序自身端口冲突 | 低 | 启动时禁止使用 20001~20050 段并给出提示 |
