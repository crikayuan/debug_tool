## 四、失败项详情与归因

### 4.1 集成用例「停止前已扫计数=0」→ **测试时机问题（非源码缺陷）**

- 现象：`scan_integration_test.py` 第 7 组，250 台范围启动后 0.6s 即 stop，`scanned=0`。
- 根因：单个无响应 IP 需遍历全部探测端口（默认 5 端口 × 500ms = 2.5s），0.6s 内尚无探测返回，故计数为 0 属正常。
- 复验：改为「先让部分主机完成再 stop」（`tests/scan_edge_test.py` C 组）→ `status=stopped, scanned=25`，**已扫结果保留（`127.0.0.1` 在 items 中）**。
- 归因：**测试代码 Bug（断言时机），已修正**。停止功能本身正常。

### 4.2 🔴 「主机名反向解析」开关无效 → **源码 Bug（尚未修复，需返工）**

| 项 | 内容 |
|---|---|
| 位置 | `backend/services/scan_service.py` → `_run_scan()`（第 236-237 行） |
| 代码 | `if not stop_event.is_set(): self._enrich_hostnames(task)` |
| 缺陷 | 调用 `_enrich_hostnames` 时**未判断** `config["resolve_hostname"]`；该开关被忽略，**用户取消勾选「主机名（反向解析）」后仍会做 DNS 反向解析**（拖慢扫描）。对比 `vendor_lookup` 有 `if config.get("vendor_lookup", True):` 守卫，说明此处为遗漏 |
| 复现 | ① 起后端；② `POST /api/scan/start` 带 `{"start_ip":"127.0.0.1","end_ip":"127.0.0.1","resolve_hostname":false,...}`；③ 结果项 `hostname` 仍为 `"Crika_yuan"`（应为空） |
| 期望 vs 实际 | `resolve_hostname=false` → 期望 `hostname=""`；**实际 `hostname="Crika_yuan"`** |
| 证据 | `tests/scan_edge_test.py` A 组 FAIL；`tests/_qa_verify.py` 在当前代码上复现：`resolve_hostname=False → hostname='Crika_yuan'`，同时 `vendor_lookup=False → vendor=''`（该开关正常） |
| 建议修复 | `if config.get("resolve_hostname", True) and not stop_event.is_set(): self._enrich_hostnames(task)` |

### 4.3 MQTT 端到端回归 7/9 ~ 8/9 → **公共 Broker 时序抖动（非本应用缺陷）**

- 现象：3 次运行分别为 7/9、7/9、8/9；失败集中为第 5 步「应用发布→对端订阅」与第 8 步「重连后订阅收报」。
- 归因实验（`diag_mqtt.py` / `diag_recon.py`）：
  - **peer→peer**（不经应用）经 `broker.emqx.io`：发布 1/1、接收 1/1 → **Broker 双向可用**；
  - **应用发布→Broker→peer**（给足订阅建立时间 3.0s）：**对端 1/1 收到**；
  - **重连后精确订阅 + peer 发布**：应用 WS **正常收到** `0A 0B`。
- 结论：失败项源于**公共 Broker（EMQX）订阅建立/发布的时序抖动**，测试脚本 1.8s 的等待在公开网络上偶发不足；本应用收发链路经隔离诊断**验证可用**。按路由规则，**环境/网络抖动不计源码缺陷**。
- 佐证：`services/mqtt_service.py`、`routes/mqtt.py` 的 mtime 为 10-14 11:0x（MQTT 增量阶段），**扫描模块未触碰**。

### 4.4 环境相关：「连接被拒=在线」在本机不生效（非源码 Bug，影响发现率）

- 设计原意（§4.1）：TCP `connect_ex` 返回 0 **或**连接被拒/RST 都判在线。
- 实测：本机环境下，**关闭端口不回 RST**——阻塞式 `connect_ex` 到关闭端口需 **~2.0s** 才返回 `10061`；而探针用 `settimeout(500ms)`，超时先返回 `10035(EWOULDBLOCK)`，故 `_REFUSED_CODES` 分支在默认超时内**基本不触发**。
- 影响：仅**开放被探测端口**或**命中 ARP** 的设备被发现；端口全关但确实在线的设备（如 `.106/.135/.138/.152`）会经 ARP 出现但标记「离线」。**不产生错误结果（保守），但降低设计宣称的发现率**。
- 归因：**环境（本机/网络对非开放端口不回 RST）+ 设计假设不匹配**，非本次源码缺陷。建议在文档/UI 注明，或二期用 ICMP 增强。

3. **改动范围核对（mtime + 内容）**：
   - **既有核心逻辑文件未被触碰**：`services/net_service.py`、`services/serial_service.py`、`routes/net.py`、`routes/serial.py` 均为 **2026-10-10** 时间戳。
   - `services/mqtt_service.py`、`routes/mqtt.py` 为 **10-14 11:0x**（属更早的 MQTT 增量），本次扫描（14:0x）未改。

> 说明：串口调试需真实硬件，本环境无硬件未做端到端；但串口源码零改动、界面结构未变，静态层面无回归风险。
